Version 0.9.7.1 · Build 6
Changes since 0.9.7.1 Build 5

GPS time service at startup
- The GPS time service waits twenty seconds before automatic synchronization. The user reported a successful restart with this delay after earlier reproducible boot failures. The exact cause remains unproven.
- Base installation, add-on update and manufacturer installation use the same delayed service definition. The startup timeout includes the extra wait; manual time synchronization remains immediate.
- The exact startup-test.conf override created during the joint test is removed when the default unit takes over. The delay is not applied twice. Other custom overrides are preserved.

Time configuration
- Already disabled network time synchronization and persistently masked time services are not configured again.
- Time-service changes suppress individual automatic systemd reloads and perform one explicit reload only when changes occur. Missing time services remain persistently masked to cover later package installation.
- Obsolete time-service files are removed only when present. Unchanged state does not cause another service reload.

Diagnostic status
- Logs show boot failures after approximately nine to ten seconds and a successful cold boot with the GPS time service running. Undervoltage was recorded during both successful and failed starts.
- Manual GPS synchronization succeeded. The startup delay is based on the user's successful test; it does not establish the full cause or rule out power-supply problems.
